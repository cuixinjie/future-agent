# T11：A/B/C 实验运行与评分

> 历史资料：保留编写时的实现、计划及验收结论，不作为当前使用说明。当前入口见 [文档导航](../../README.md)。

> 2026-10-27 普通主线已改造。本页保留原阶段、分步人工/旧实验路径与当时验收语义；默认chat的自动研究、交付类型、时点和新合同见[预测主线改造决策](../decisions/预测主线改造.md)。旧冻结、协议及历史验证结果不改写。

T11 提供本地顺序执行的实验工具，复用现有事件、正文快照、人工审查、预算、预测和冻结服务。离线测试验证程序行为；不代表真实模型能力、发布预测效果或独立评估已完成。真实批次仍属 T12。

## 数据流与边界

`锁定协议 → evaluation init（全部项目×A/B/C登记） → 现有C流程准备 → evaluation seal → A/B/C执行与封存 → 项目共同核验 → report`。

C 的读取、澄清、资料导入/检索及评估沿用原命令，在 Tc 前完成。研究可以部分完成，但必须保留缺口；数据资格不足时 C 正常输出情景。封存后只运行预测，不再联网补资料；新增答案、事件版本、证据、审查或配额改变会导致输入检查失败。B 只读取共享原文、全部澄清答案、协议项目规则、相同的完整历史正文及人工整理的历史记录，不接收 C 的事件档案、研究结论、审查结论或概率。应在 B 之前完成并封存所有共享答案。

一个项目使用一个专用 C 会话，各项目不能共用会话；不要在实验期间将该会话用于其他任务。B 也通过现有 ModelCalls 消费该会话预算，保持 Reader、研究、B、C 总调用/token/时间及搜索/网页配额。B 只有一次结构化调用，不重试、不修复；C 沿用有限修复/重试。所有调用先持久化归属和预算预留，未知用量保留未知与保守额度。

协议方法必须匹配已执行实现：

| 组 | 方法版本 | 提示词 | 模型 |
|---|---|---|---|
| A | `release-frequency-1.0` | 无 | 无 |
| B | `direct-1.0` | `direct-1.0` | 与C相同的明确版本 |
| C | `judgment-1.0` | `forecast-1.0` | 与B相同的明确版本 |

协议统一开启 B/C 数值请求，C 审查须 `allow_numeric=true`；关键资料缺口仍可使 C 走情景或拒绝，不能单独关闭 C 的数值请求来改变实验条件。B/C 的实际最终输出 token 额度必须等于协议值（同时匹配模型配置 `LLM_OUTPUT_TOKENS`）。真实 C 需要会话历史中有同模型 `reader-1.0` 的读取版本；人工确认另存为 manual 版本是正常行为，任何 fixture 历史、夹具研究和夹具证据不能用于真实协议。各项目预算须在创建 C 会话时即不超过协议；不得先消费后放宽。当前无价格配置，`budget.max_cost` 必须为空；有金额上限的协议明确拒绝启动，不假称已执行金额限制。

## Tc 与 T0

协议的 `evidence_cutoff=Tc`、`forecast_at=T0`，事件发生窗口固定为 `(T0,T0+30×24小时]`。现有通用评估以事件问题的 `forecast_at` 作为证据截止时间，因此实验 C 问题使用 `forecast_at=Tc`，`window_start=T0`；不修改既有 Forecast 合同。可用下面的模板直接生成，省去手动改时间：

```powershell
uv run --locked future-agent release-template --project project.json --forecast-at "2099-01-01T01:00:00Z" --evidence-cutoff "2099-01-01T00:00:00Z"
```

未传 `--evidence-cutoff` 时保留原模板行为。事件的目标文字、结果规则、窗口及核验来源必须逐项匹配协议模板。输入须在 Tc 前实际取得、入库和封存；允许提前封存，封存后不能补充。旧发布日期不能证明动态正文在 Tc 可得。协议登记、快照和提交均保留实际时间；共同 T0 之后的结果保存为 late，保留产物但不评分。数据库写入边界再次检查 Tc/T0。

## 历史资料与基线

历史源必须匹配项目登记的 `history_source`，正文属于 C 事件版本并通过截止资格；C 的人工审查需包含该正文的完整引用，以保证 B/C 使用同一份历史资料。`ReleaseHistory` 保存正文 ID、覆盖起止、完整性、审查人、完整性声明原文及逐版本记录原文。具体发布分类、版本命名、分支/组件范围和历史记录完整性仍由人工核对；程序无法仅凭一段网页证明官方记录没有遗漏。不得将搜索片段、未知获取时间或夹具资料用于真实历史估计。

`coverage_end` 必须为 Tc，起点不晚于 `Tc−360天` 且 `complete=true`，A 才能计算。第 j 个窗口为 `(Tc−30j天,Tc−30(j−1)天]`，j=1…12；按“窗口是否有至少一次稳定发布”计数，p=Σz/12。同通道版本号忽略大小写及前缀 v 后去重；同版本时间或资格冲突拒绝计算。排除其他通道、draft、显式 prerelease、alpha/beta/RC/nightly/preview/dev 及人工注明的项目特有排除项。补丁稳定版计入，编辑旧说明不能登记成新发布。缺失完整历史使 A missing，不能补0或0.5。

## CLI 运行与失败处理

下列命令中的 ID、文件及时间均需替换为本地实际值。新协议可参照 [T11夹具协议](../../../examples/protocol.t11.fixture.json) 的方法声明；旧 [M1夹具协议](../../../examples/protocol.fixture.json) 保留历史原文，其方法版本不满足 T11 执行条件。已有锁定协议不升级、不改写，需要执行新实现时新建协议/批次。

```powershell
uv run --locked future-agent protocol create --input protocol.json
uv run --locked future-agent protocol lock <协议ID> --expected-version 1
uv run --locked future-agent evaluation init <协议ID>
# 先按既有命令完成各项目的读取/澄清/确认、证据和评估，再在Tc前封存：
uv run --locked future-agent evaluation seal <协议ID> --input sealed-input.json
uv run --locked future-agent evaluation run <协议ID> <项目ID> A
uv run --locked future-agent evaluation run <协议ID> <项目ID> B
uv run --locked future-agent evaluation run <协议ID> <项目ID> C
uv run --locked future-agent evaluation show <协议ID>
uv run --locked future-agent evaluation report <协议ID>
```

`init` 一次性保存协议的全部项目×三组。重复初始化拒绝，已有终态再次 run 返回原记录。模型配置、目标和封存依赖等执行前检查错误会明确报错，条目仍保持 waiting，可在共同期限前纠正配置；开始执行后，失败、拒绝、情景及迟交分别保存，不把失败当作空成功。

B/C 都使用相同 `ForecastDraft` 和 `yes/no` 结果结构。A/B 作为实验专用产物不可覆盖地保存在条目中，保存输入哈希、完整结果、输出哈希、实际方法/提示词/模型版本；C 同时关联 T10 的独立 FrozenForecast。实验只收集首次预测，更新不能替换条目。

取消、显式缺失及截止收口：

```powershell
uv run --locked future-agent evaluation cancel <协议ID> <项目ID> C --reason "用户取消"
uv run --locked future-agent evaluation missing <协议ID> <项目ID> B --reason "调用中断，结果与费用未知"
# T0之后执行，给仍未执行/完成的条目保存原因；可重复执行：
uv run --locked future-agent evaluation finalize <协议ID>
```

运行前保存 running，外部调用前保存预算。进程退出后不会自动重试实验首次条目，也不会恢复费用为0；先检查 `evaluation show` 和会话记录，再显式登记 missing。若会话仍在 FORECASTING，继续其他组前按 T10 的 `forecast abandon <会话ID>` 显式结束中断状态，原预算不重置。取消 C 同时通知既有预测步骤；迟到的结果不能恢复已取消条目。T10 的一般预测仍保留原恢复能力；不将手工重试后的结果自动回填为原实验提交。

## 共同核验、人工质量审查与评分

使用 `evaluation resolve` 按项目追加一条所有组共用的结果核验；没有 C 概率也可核验 A/B。核验复用 T10 的 Resolution 合同和窗口规则，结果必须引用项目冻结的 `official_resolution_source` 的已保存正文片段；并核对正文快照与引用。结果键为 yes/no，resolved 必须有引用；pending/disputed/void 不携带结果。完整窗口前不允许判 no；yes 需提供窗口内实际 `observed_at` 才能提前登记。宽限7天不改变事件窗口，之后补核验继续追加历史，不改旧记录。

```powershell
uv run --locked future-agent evaluation resolve <协议ID> <项目ID> --input resolution.json
# 再次登记需要带最新核验ID，防止覆盖并发变更：
uv run --locked future-agent evaluation resolve <协议ID> <项目ID> --input disputed.json --expected-previous <核验ID>
uv run --locked future-agent evaluation review <协议ID> --input quality-review.json
```

`resolution.json` 使用既有 `ResolutionInput`，见 [T10说明](12-T10冻结核验与恢复.md)。实验核验存于实验内，`forecast_id` 使用该项目 C 条目的稳定 step_id 作为共同核验键，不伪造 A/B 的通用 Forecast。一般 `resolution record` 的历史与实验核验分开保存，需用上述实验命令登记实验结果。

质量审查 JSON 包含 `project_id`、`arm`、`reviewer`、非负整数 `citation_errors`、`fact_omissions` 和 `reason`。审查追加保存历史，报告使用最新审查；没有人工审查时保持空值，不能假装0错误。

报告保留全部预登记条目、失败/迟交/拒绝原因、数值覆盖率、情景/拒绝率、核验状态、各组 Brier、C−A/C−B 的配对共同项目、ABC共同子集以及各项目调用/token/搜索/网页/耗时和费用。二元 Brier 是 `(p_yes−y)^2`，配对负值表示 C 在该共同子集误差更低。整批30天窗口结束前不计分，即使已提前核实 yes；报告生成时间是共同核验截面。后续状态更正重新生成报告会更新分数，可用 report 的 `run_version`、`resolution_id` 和预测哈希追溯原输入。

费用、真实 token 用量或中断耗时未知时为空；另列保守 token 预留。C 成本包含封存前 Reader/研究及 C 预测，B 成本只含其直接调用；二者使用同一个项目总预算。后续无关会话调用不混入已提交实验成本。不对选择性输出的共同子集宣称普遍胜出，不自动调参、校准或训练，不输出忽略项目相关性的置信区间。

## 合同、升级与回退

新增实验、输入、条目、历史记录、产物和人工审查合同均为 schema 1.0；新增 `direct-1.0`，现有 `reader-1.0`、`forecast-1.0`、`judgment-1.0`、协议/会话/预测/冻结合同不变。评估规则升为 `evidence-assessor-1.2`：发布基线已实现，但通用路径仍缺专用历史资格，不会出现在普通预测可用方法中；旧1.0/1.1评估保留并标记失效，下一次普通预测需重新评估。历史预测、实验协议、冻结原文与哈希不改写。

Alembic `0006_evaluation` 只新增 `evaluation_runs` 表，内含全登记列表、不可覆盖的快照/产物与追加核验/审查历史；使用乐观版本校验和事务，拒绝删除条目、重置终态或改写封存内容。没有新依赖，也没有 API、队列、工作者租约或 UI。启动 CLI 会迁移数据库；升级前停止相关进程并备份**完整 DATA_DIR**（数据库及正文快照），回退恢复完整备份。迁移拒绝破坏性降级，旧程序不能操作新实验，不能只回退数据库版本号。
