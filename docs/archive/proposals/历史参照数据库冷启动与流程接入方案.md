# 历史参照数据库冷启动与流程接入方案

日期：2026-11-03。状态：原始设计方案，部分工程能力已实现，真实冷启动与效果验收未完成；当前状态及操作见[开发计划](../../05-开发计划.md)与[操作说明](../../guides/历史参照数据库.md)。以下实施顺序与预算保留为设计依据，不表示全部已经执行。任务状态统一见[开发计划](../../05-开发计划.md)，本方案细化既有Q01（评估输入）和Q02（普通参照），不另设平行任务体系。

## 1. 目标与首版选择

把公开历史资料整理成能够回答“在什么时点、什么条件下、类似事件后来怎样”的可追溯记录，并在普通预测中提供程序计算的参照。没有真实用户也能开始收集和验证。

吸收参考图片中的四点：问题带明确期限；事前材料与事后结果分开；AI整理、程序校验；用回放和前瞻结果检验方法。图片中的概率、案例和Brier分数都是示例，不作为种子数据或效果依据。

首版沿用SQLite、SQLAlchemy/Alembic和现有快照存储。以“同一公开软件产品/通道未来30天至少一次稳定发布”为首个统计适配对象；公开跨领域题库作为开发评估输入。保留通用用户入口，按问题族声明参照能力。

**两条数据线分别入库、分别使用：软件发布记录用于可计算参照；公开预测题用于开发诊断和对照。** 一批跨领域题的“发生比例”不能充当任何新问题的基础概率。首版不建通用向量库、知识图谱，不自动训练、聚合或校准，不新增常驻采集进程。

## 2. 已有基础与需要补充的能力

| 现有实现 | 本方案如何复用／补充 |
|---|---|
| ResearchService、EvidenceDocument、Snapshot、EvidenceSpan | 复用受控网络、原文快照、哈希和引用；新增独立历史数据入口，避免必须为每条历史案例创建聊天会话 |
| domain/evaluation.py中的ReleaseHistory、baseline | 复用稳定版筛选、去重、12个完整30天窗口纯规则，不复制算法，不改变release-frequency-1.0 |
| AnalysisPlan、EvidenceReading、NumericBasis | 目标规划后匹配参照能力；阅读中解释适用性与差异，不让模型重算历史比例 |
| AssistanceService → AssessmentService → ForecastService | 增加有类型的参照输入与资格审查；普通流程、CLI和Web共享服务 |
| 冻结、修订、核验、软件发布实验评分 | 复用原语；新增参照快照及通用历史评估合同，不能把旧实验器称作通用题库评估器 |

代码已有reference_basis、differences_and_adjustment和反面解释审查字段，但它们尚不是结构化参照计算结果。本方案中的表、服务和字段名均为拟议名称。

## 3. 冷启动数据从哪里来

### 3.1 软件发布数据：先做一个可复算的小库

使用GitHub官方Releases接口与项目自己的发布公告。官方接口提供发布列表、分页和draft/prerelease等信息；它不包含所有普通Git标签，因此目标必须明确限定到约定发布通道，不能把Releases当作项目一切发布的全集。[接口说明](https://docs.github.com/en/rest/releases/releases#list-releases)

建议首批流程：

1. 登记20个候选仓库及产品/稳定通道，覆盖不同发布节奏；可从CPython、Node.js、TypeScript、pandas、NumPy等候选中审计，名单不代表它们都满足数据条件。
2. 先固定候选名单、采样日期、入选规则和排除规则，再读取未来结局。历史采样不能按今天的活跃程度或未来是否发布挑项目；无法恢复当时名单时注明选择偏差，仅作开发样本。
3. 每个项目抓取覆盖截止前至少360天的全部分页；保存原始响应、分页链、请求时间、哈希及接口版本。按published_at处理发布时点，不能用提交时间或created_at替代。
4. 核对产品映射、稳定通道、版本资格、重复版本和来源覆盖；多产品仓库不能按仓库名直接混合。
5. 只有覆盖完整且无资格冲突的项目，才生成12个相邻、互不重叠的30天标签；缺页、限流、超时均保留缺失。
6. 首批最多形成20×12＝240个窗口标签。这不是240个独立项目，也不是样本充分性或效果结论。

完整性不是“API返回200”。必须核对分页是否结束、最旧覆盖是否足够、过滤前记录是否完整、项目是否以其他通道发布。即使分页齐全，删除或后续编辑仍可能影响历史重建；只对锁定通道声明覆盖，不声称还原当时互联网全貌。未找到正例只有在相应窗口完整覆盖时才可标0。

### 3.2 公开题库：先做50题结构先导

优先采用ForecastBench发布的固定提交数据包，记录提交SHA、文件清单、哈希和来源。其官方数据仓库声明CC BY-SA 4.0；导入时保留许可与归属，并逐文件检查是否含需要单独处理的上游材料。[官方数据仓库](https://github.com/forecastingresearch/forecastbench-datasets)

先导上限50个不同事件族的二元问题，按事先固定的年份、领域和期限分层，再用固定随机种子抽取；不按是否预测正确挑题，不强行凑成正负各半。抽样和清洗前后都报告实际分布。个人预测条数、多个期限和多次更新均不能直接当独立题数。

优先检查问题原文、规则版本、预测时点、窗口终点、结局状态、结果依据和事前材料是否能配对。沿用已有研究记录中的(source, id, resolution_date)作为待核对的来源匹配候选，保留原始键；若有规则修订还需加入规则版本，不能只按标题合并。缺少事前证据的题可以用于目标/结果解析诊断，不能伪装成完整研究回放。

首轮仅用静态可追溯包，不要求直接爬取Metaculus或Good Judgment Open。已核对的Metaculus现行条款对自动提取及AI开发用途有限制；其API可访问性不能自动解释成数据可用于本项目开发。直接接入作为后续来源专项审查，当前不依赖它完成冷启动。[平台条款](https://www.metaculus.com/terms-of-use/)

### 3.3 无用户前瞻积累

在历史先导开发期间准备10—20个合格软件项目的未来30天问题；正式预测须在方法、名单、预算和核验规则锁定后生成并冻结。提前收集事前快照，窗口结束后核验全部登记项。数量仅是工程先导规模，效果检验样本量另按先导变异和目标差异确定。

## 4. 数据库保存什么

图片的四张表覆盖了问题、证据、结果和回测，适合作为逻辑起点。我们还需要数据集版本、参照结果和输入快照；否则无法解释“这次到底用了哪批历史”。以下是逻辑对象，不要求一次落成七张物理表。

| 拟议对象 | 必要内容 | 使用边界 |
|---|---|---|
| DatasetRelease | 数据集ID/版本、来源提交、许可、采集批次、清单哈希、选择规则、切分清单、审查记录 | 发布后不可覆盖；更正新版本 |
| HistoricalCase | 来源键、事件族/对象、问题族、问题/规则版本、事前截止Ti、预测窗口、产品/通道、状态、排除理由 | 不携带结局字段；跨平台同事件保留来源并建立事件族关系 |
| HistoricalEvidence | case_id、角色（事前/结局依据）、快照ID/哈希、精确片段、published_at、modified_at、retrieved_at、imported_at、archive_capture_at、日期精度、来源组 | 复用快照底座；程序按角色、时间和用途投影 |
| HistoricalOutcome | case_id、结果版本、yes/no/unresolved/disputed/void、可空标签、结果发生时间、结局首次公开时间、核验/入库时间、依据、审查来源 | 由标签仓储提供；不是ForecastService依赖 |
| ReferenceEstimate | 请求/事件版本、数据集版本、参照类型、过滤规则、纳入/排除清单、分子/分母、逐窗口标签、可空值、适用性、限制、方法版本、哈希 | 程序计算；保存原值，不交给模型重写 |
| ReferenceBinding | 会话/最终事件版本、截止Tc、ReferenceEstimate哈希、白名单输入哈希 | 每次预测固定；恢复不读取“最新数据库” |
| EvaluationRun | 协议/切分/题目版本、证据包和参照包哈希、模型/提示词/方法/代码版本、预测/失败/拒绝、调用和成本、评分关联 | 预测记录先封存，评分后关联；评分不能覆盖预测 |

每条AI提取特征还保存原文位置、提取版本、审查来源和未知状态。模型可以候选分类、整理字段和解释相似性；不能自己填发布日期、补结果、把未确认分类升级为人工审查。

HistoricalOutcome的发生时间与“何时知道结果”必须分开；例如某年财年已结束不意味着当时已经公开盈利结果。图片中的“历史参考概率40%”不作为案例固有真值保存：它应是某个版本参照查询的计算产物，或有时点及来源的外部预测记录。

物理实现可用SQLite索引列加版本化JSON payload，延续现有风格；大正文保存在内容寻址快照目录。预测应用只接收白名单投影，不直接导出整行JSON。首版是本地单用户的应用边界隔离，不宣称SQLite表本身提供跨用户安全隔离；若未来运行不受信任工具，评分标签应另库并由独立进程持有。

## 5. 时间、结局和用途如何隔离

设Ti为历史案例当时的预测截止，Wi为其结果窗口，Tc为当前目标的证据截止。所有时间带时区，保存UTC；只有日期而无精确时间时记录精度，无法证明先于截止则不进入严格路径，不任意补为零点。

| 用途 | 可用内容 | 程序规则 |
|---|---|---|
| 当前普通预测的历史参照 | Tc前已经有依据的历史记录与已知结局 | 原始记录及结果依据必须实际在Tc前获取/入库；参照可在Tc后仅对已封存输入纯计算并记录生成时间，不得补入Tc后取得的事实 |
| 严格前瞻实验 | 本地在Tc前实际封存的材料与参照 | 沿用现有eligibility和实验规则，不豁免迟获取、迟入库 |
| 历史开发回放 | 今天取得但有依据声称在Ti前可见的材料 | 独立retrospective合同和命名空间，保存真实获取时间、历史可见性依据及污染风险；绝不回填时间冒充前瞻 |

对历史回放的参照库也必须做as-of查询：只允许在目标Ti以前已经公开结局的其他案例，且这些案例的特征来自各自事前时点。排除当前题及同一事件族、共享结局、多期限衍生题；不能只屏蔽当前题的outcome，却让它的答案经参照统计返回。

已解决的历史案例结果可由ReferenceService读取并汇总成合格参照；当前待预测问题及封存测试集的答案只允许评分用例访问。这两种用途必须区分，不能一概禁止读任何历史结果，也不能把标签仓储交给模型工具。

历史数据物理上知道答案，不等于预测上下文可以知道。预测输入按字段白名单构建，不使用“序列化整个对象后删outcome”。白名单还须排查标题后缀、结局解释、URL/文件名、后续修订正文、他人预测及理由中的答案暗示。历史回放默认关闭实时网页搜索，只在封存事前包内检索；需要扩大包时另建版本并重新标记开发用途。

同一事件族全部进入同一开发/选择/封存测试分组，再按时间安排；冲突时整族隔离或排除并记录理由。开发用过的样本不能继续声称独立测试。保留训练记忆风险，历史回放不能替代未结局前瞻验证。

## 6. 参照怎样检索和计算

### 6.1 先硬匹配，再解释可比性

系统从AnalysisPlan生成ReferenceRequest：问题族、对象/产品、通道、结果定义版本、窗口长度、截止、用途及事件族排除集。模型可以提出候选映射，程序负责必需条件检查；映射不明确时保留不适用，不擅改用户问题凑基线。

首版用SQLite结构化条件检索。只有问题定义、期限、产品/通道、时间资格和覆盖一致才计算。相似文字、行业相同、搜索排名都不能直接变成统计权重。

### 6.2 第一个可执行算法

对匹配“同一产品/通道未来30天至少一次稳定发布”的目标：

1. 构建经审查的ReleaseHistory，覆盖截止前360天，并记录完整性依据。
2. 调用现有baseline(history, cutoff, channel)，取得12个0/1标签；沿用原函数边界，不重新定义一套窗口。
3. 程序计算p_ref＝sum(labels)/12，保存标签、分子、分母和输入哈希。
4. 显示为“历史窗口频率”，同时保存12窗口依赖、小样本、发布节奏变化、缺少距上次发布条件等限制。

0/12和12/12允许作为真实观察频率，但不声称未来绝不/必然发生；这与禁止用0填缺失是两回事。首版不加任意平滑先验，不把频率线性缩放到90天，不把不同项目混成总体成功率。

### 6.3 逐步扩展参照类

后续公司盈利、产品发布等题族须各自定义采样总体、单位、时点、期限、成功/失败/未结局规则与覆盖证据。先按事前条件形成候选全集，再核验全部结果；不能只找成功案例后计算比例。

如果某题族定义成立，可计算k/n，同时报告未结局数、排除数、独立事件族数和选择偏差。没有合理分母、样本由成功故事拼成、目标跨度不同或条件只能靠事后总结时，只提供案例参照，不提供基础概率。最低适用规模与统计区间需通过该题族开发研究确定；不设置“20条就可靠”的通用门槛。

首版返回三种内容状态：computed（可复算且适用）、qualitative_only（可读案例但不支持比例）、not_applicable（定义/数据不匹配）。执行错误独立为failed，记录具体原因；不能转成not_applicable或空成功。

## 7. 如何接入我们现有流程

拟议数据流：

用户叙述 → Reader提取 → AnalysisPlan明确目标 → 本地候选参照查询 → 有界研究与阅读 → 固定最终截止Tc及事件版本 → 重新检查并封存参照 → 资格评估 → 最终判断/反面审查 → 保存报告 → 冻结/修订 → 核验并生成候选历史记录。

### 7.1 两次参照检查，各有用途

**目标确定后**：AssistanceService调用拟新增ReferenceService，查本地数据集能否支持目标，取得覆盖缺口。例如项目缺失一页发布历史，可成为后续公开研究缺口。它不是最终参照，不允许后续直接复用而不检查截止。首版使用已有授权查询和预算补齐，不新增隐式联网通道；机器接口来源须由专用适配器校验公开对象和主机。

**研究完成、最终事件生成后**：在execute中现有_target(final=True)、证据关联完成之后、AssessmentService.assess之前，针对最终事件与Tc重算/验证参照，绑定不可变数据集版本。此步骤是纯本地计算；所有必要来源和提取审查应在固定Tc前已保存。若冻结参照前发现缺少资料，返回缺失；若继续研究，必须重新固定截止、事件版本及下游产物，不能往旧截止里补数据。

已有baseline以cutoff为历史窗口边界；普通流程的未来窗口可能从生成预算之后开始。接入时明确保存“历史锚点Tc→未来窗口起点”的间隔，不伪称二者完全相同。首版仅接受普通相对30天目标和现有预算边界内的短延迟；延迟上限按本次锁定配置预先确定并写入参照方法版本，超出则失效/重算。任意延后起点或绝对未来窗口先返回不适用，后续另建算法验证。

### 7.2 模块职责和拟议接口

| 位置 | 改动职责 |
|---|---|
| domain/reference.py（拟新增） | ReferenceRequest/Estimate、匹配与完整性规则；调用现有发布基线，纯计算无网络/ORM |
| application/reference.py（拟新增） | 声明HistoricalReferenceRepository端口，组织查询、审查和不可变参照封存 |
| providers中的专用来源适配器（按需） | 拉取官方数据和分页、记录真实时间、限流及失败；不负责判断概率 |
| storage | 实现仓储、数据集版本和索引，复用内容快照；不能改写历史条目 |
| application/assistance.py | 注入服务、安排上述两个时点、持久化绑定；新事件使旧绑定失效 |
| application/assessment.py | 分开审查来源资格、参照适用性与最终数值资格；已计算参照不自动授予最终概率资格 |
| application/forecasts.py及领域输入 | 显式接收封存参照/绑定，加入步骤输入哈希和恢复校验，不向模型开放仓储查询 |
| prompts/assistance.py | 提供参照摘要与差异审查要求，模型解释当前证据如何支持调整 |
| forecasting/report.py与Web投影 | 渲染程序保存的参照和模型判断；CLI/Web不另算一次 |
| cli.py/config.py | 组合入口装配仓储和服务；默认方法准入前通过显式开发配置启用 |

应用层端口只需表达lookup_candidates(request)、save_estimate(estimate)、get_estimate(id)等实际用例；结果标签读取放在专门参照/评分端口，ForecastService不依赖它。无需预建插件框架。

### 7.3 给模型什么、要求模型做什么

提供：参照类型、k/n和原始频率、覆盖时间、产品/通道、定义、适用限制、合格来源引用、当前证据。默认不把整库案例或测试结果交给模型。

要求：说明目标与参照是否可比；解释发布计划、维护状态等当前证据及反证；形成有依据的最终交付；保存differences_and_adjustment及最强反面解释。模型不改写k/n，不编造调整系数，不将参考频率称为已校准最终概率。

参照与当前证据都可用不意味着必须给数字。已有insufficient/来源门槛继续保留；要允许“合格参照本身作为数值依据”，须新增带类型和来源链的资格规则及失败路径，不能仅将NumericBasis.status改为supported绕过现有门禁。新规则不能把模型说明当人工完整性确认。

### 7.4 报告怎样呈现

以下全部为演示数字，不是已采集记录或真实预测：

> 问题：该产品未来30天是否至少发布一次稳定版？
>
> 历史参照：过去12个完整30天窗口中，8个有稳定发布，观察频率66.7%。
>
> 当前差异：已公告发布候选版，但仍有阻塞问题。最终判断示例为70%，属于未经校准的主观概率。
>
> 调整依据：说明哪些已读证据支持比历史频率略高，并保留反面解释。
>
> 限制：历史窗口相关、发布节奏可能变化，参照没有显式建模距上次发布的时间。

66.7%由报告渲染保存的8/12结果；最终70%由预测产物提供。若当前依据不足，报告保留66.7%的观察事实并说明无法形成最终数字，不让报告构建器自动取参照值充当最终概率。

### 7.5 没有参照、数据失败和更新

无匹配数据：照常研究，交付有依据的未校准判断、方向、条件或无法判断，并标记“未使用统计历史参照”。已启用参照查询执行失败：记录执行故障及影响；若当前证据独立支持判断可明确受限交付，若任务依赖参照则执行未完成。不能悄悄用模型记忆补数据库。

修订：新证据或新数据集只影响新预测版本；旧冻结内容、参照绑定和成本不覆盖。到期核验只产生候选历史记录，需检查规则、来源资格和争议后发布到新数据集；模型审查不能自动变成人工确认。数据获取、提取和核验均保留预算与未知费用。

## 8. 回放、消融与验收

第一项要测的是“加入历史参照是否有帮助”，无需一开始同时加入多路聚合与校准。

| 对照 | 目的 |
|---|---|
| 现有发布历史频率 | 最简单的数据基线 |
| 同模型一次直接预测 | 成本参照，不作为唯一强对手 |
| 同模型、同工具权限和预算的研究助手 | 判断流程相对强对照是否有价值 |
| 当前系统，不加结构化参照 | 现有普通流程对照 |
| 当前系统，增加结构化参照 | 唯一新增因素；保持模型、当前证据、审查规则和预算一致 |

固定证据包的参照有/无实验用于判断“利用参照”收益；端到端同预算实验另测研究行为差异。历史数据采集与人工准备成本单列，并说明复用次数；不能只报预测调用成本。旧软件发布A/B/C协议不修改，扩展组使用新协议版本。

保存全部登记题、首次预测、拒绝、条件/方向交付、失败与费用未知。共同可评分子集报告配对Brier差值mean((p-y)^2)，同时报告全体覆盖、成本、延迟、目标忠实度及样本选择情况；缺失概率不补0.5。按项目/事件族而非240个相关窗口估计不确定性。先导规模不支持优势结论，正式样本量和准入阈值在锁定测试前另定。

必须覆盖的验收用例：

- 正常：同产品/通道/30天，完整360天历史；分子、分母、标签、哈希能复算。
- 数据边界：缺页、超时、空列表、日期不明、版本冲突、草稿、预发布、错产品、错通道、错期限、未来记录、后续修订。
- 时间边界：截止瞬间、历史窗端点、目标起点延迟、Tc后抓取/入库、历史回放不得伪装前瞻。
- 标签隔离：目标结局、同事件族答案、结局解释和文件名暗示不得进入模型输入；未来案例不得进入参照分母。
- 状态：不匹配与执行故障分开；中断恢复不重置预算、不重新选最新数据；事件/规则/数据版本变更使绑定失效。
- 交付：参照非空不强制概率；没有参照不自动拒绝；报告不重算或编造结果；旧冻结哈希和旧实验不变。
- AI质量：完整性、产品映射、提取特征和证据适用性独立抽查，测错误接受和错误排除，不能仅靠JSON合法验收。

## 9. 实施顺序、预算和交付物

以下为实施先导的建议上限，不是已执行结果或统计门槛；保持Q01先行、Q02接入、Q05前瞻的原依赖。

| 步骤 | 交付物与停止条件 |
|---|---|
| 1．锁定采集清单和用途 | 20仓库候选、50题抽样规则、来源许可记录、字段映射与预算；未知权限来源不作为首批依赖 |
| 2．先做5项目＋10题端到端导入 | Q01数据包/字段白名单/标签隔离、幂等导入、排除日志和人工抽查；先导未通过不扩大 |
| 3．扩到首批上限并发布数据集v1 | 最多20项目、50事件族；实际合格数可少于目标，不为凑数填补；保存全部失败 |
| 4．Q02实现发布参照纯计算与仓储 | 复用baseline、ReferenceEstimate、缺失/失败分类；验证逐窗口复算、时间和版本 |

| 6．先导消融并登记前瞻批次 | 不加参照/加参照配对；方法选择后锁定未来名单，冻结并到期核验，不边测边调 |

首轮采集建议单批最多200个HTTP请求（含重试）、30分钟累计主动执行时间、100MB原始响应，单响应仍受现有抓取大小上限；任一预算先到即停止并保留断点，不表示数据已完整。提取首批优先确定性JSON解析，不调用模型。确需模型辅助时，先锁定独立批次额度（建议最多20次、100000总token、20分钟），预算口径含修复/重试并与会话分开登记；价格未知不报零成本。该方案本身不触发真实模型调用。

前瞻单题沿用现有会话预算，批次总费用/用量上限须在运行协议中另锁定。准备、获取和核验成本均计入报告。没有已知真实价格和模型配置时，不预估一个貌似确定的金额。

首版完成标准是“能够导入、可复算、正确隔离、在普通流程显示真实参照并保留失败”，不是“拥有1000条记录”或“准确率提高”。效果准入另需独立前瞻结果，未改善也须保留。
